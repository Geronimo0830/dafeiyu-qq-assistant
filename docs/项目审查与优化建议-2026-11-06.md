# 项目审查与优化建议

审查日期：2026-11-06。对象：当前本地源码。此报告没有实施修复，没有提交或上传代码。

后续进展：用户确认 A/B/C 方向后的实现见 [2026-11-08 改造记录](改造记录-2026-11-08.md)。下文保留审查时的现象与证据，文件行号和行为不代表修复后的版本。

## 结论

建议保留现有 Python 服务端、原生网页和海洋蓝界面，先修复数据处理、费用确认、安装恢复及错误反馈。当前还不适合交给普通用户作为稳定安装包使用。没有证据要求立即更换整个技术栈。

本轮确认了 10 个问题或不安全行为，其中 7 个通过 Python 临时目录/模拟依赖验证，3 个通过真实前端函数与模拟 DOM/API 验证。这里的“确认”指下述明确行为；不代表已在真实用户机器造成数据损失、产生费用或完成远程攻击。

## 范围与验证

- 阅读自有 `app/`、`build/`、`dev/`、`tests/`、主要文档，并核查调用关系和异常路径。
- 第三方代码不做逐行审计，只检查本项目如何写入配置、导入插件、管理其进程和数据。
- 原有测试：`python -m unittest discover -s tests -t .`，112 项通过，29.532 秒。
- 定向复现：`.tmp/project-review/verify_findings.py`、`verify_frontend.cjs`，结果分别存入同目录的 `evidence.json`、`frontend-evidence.json`。
- 复现仅使用合成凭据、临时目录和拦截的进程/API调用，没有访问真实 QQ 数据，没有调用付费接口。前端定向复现是函数级模拟，不是完整浏览器验收。
- 未进行真实安装包构建、真实 QQ 登录、真实语音/记忆调用和干净 Windows 实机验收。
- 并行审查因工具额度中断，最终结论由主审继续核实，不将未完成的独立审查当作背书。

## 优先修复的问题

P1：普通用户交付前优先修复；P2：可靠性和交互问题，应纳入下一轮修复。

### 1. P1：切换账号会删除小号的整个 QQ 数据目录

- 位置：`app/services.py:113`、`:124`、`:128`；调用来自 `app/server.py:263`。界面承诺在 `app/web/app.js:530`。
- 触发：使用“更换 QQ 小号”。`clear_qq_login()` 调用 `forget_qq_account()`，后者递归删除 `Tencent Files/<QQ>`，没有只限于登录凭据。
- 证据：模拟账号目录中的 `nt_db/history.db` 也被删除。现有测试甚至把“整个账号目录消失”作为成功条件。
- 影响：该小号在本机正常 QQ 客户端中的数据可能一起丢失；界面“聊天记录保留”无法覆盖这一行为。
- 建议：切换账号只清理本项目持有的登录状态，优先使用组件提供的退出接口。删除外部账号数据应独立成明确选项，并有备份和路径校验。需先核实目标 NapCat 版本的退出接口，不能猜接口名。
- 验收：保留模拟 QQ 聊天库和用户文件，旧账号不能被本项目自动重新登录；共享目录不受影响。

### 2. P1：语音锁未覆盖保存连接设置的后台调用

- 位置：`app/server.py:37`、`:144`、`:150`、`:156`；`app/web/app.js:234`、`:270`。
- 触发：重新打开控制台，语音仍锁定，所有已保存凭据留空，仅保存 QQ 号或其他连接设置。
- 原因：前端允许沿用语音凭据，后台恢复旧值后无条件调用 `_check('doubao')`；校验缓存只在本次进程内有效。
- 证据：新 App 的模拟请求中，豆包检查函数被调用 1 次。真实函数会发起 TTS 请求，可能产生费用。
- 建议：区分“沿用已保存凭据”和“验证新凭据”；收费校验需要服务端接收并验证明确的本次操作确认。编辑名字/QQ 等不相关项目不应触发 TTS。
- 验收：锁定且凭据未变时，保存和应用设置的完整链路不调用 TTS；确认后每次校验不重复发起。

### 3. P1：中断安装可能直接进入控制台，无法按流程继续

- 位置：`app/main.py:57`、`:67`；`app/server.py:46`、`:248`。
- 触发：安装已经产生 `state.json`，但只完成解压等前期步骤，随后进程退出或重启。
- 证据：状态仅有 `done=['extract']`，入口仍返回 `status` 模式。控制台的启动操作只启动服务，不补齐完整安装流程。
- 建议：明确区分“未安装、安装中、可恢复、已安装、需要修复”；根据已完成步骤及关键产物决定入口。恢复应复用已有设置并继续未完成步骤。
- 验收：分别在解压、配置、导入、扫码阶段中断后重开，能继续对应阶段，而非误进控制台。

### 4. P1：更新入口先删除旧文件，失败后没有回退

- 位置：`app/installer.py:177`、`:191`、`:192`。
- 触发：启动新版安装程序，同步 `app/` 时遇到权限、文件占用或磁盘错误。
- 证据：模拟 `copytree` 抛出 `PermissionError` 后，函数返回 `False`，旧版 `app/main.py` 已不存在。
- 建议：先复制到独立暂存目录并校验，保留旧目录，成功切换后再清理；失败必须恢复旧版本并提示原因。新增版本标记，防止旧安装包意外降级。
- 验收：复制失败、切换失败时旧版仍能启动；升级不覆盖凭据、角色、聊天和记忆数据。

### 5. P1：多个窗口保存状态会相互覆盖

- 位置：`app/store.py:83`、`:109`；`app/main.py:72`。
- 触发：安装窗口与控制台持有不同时间读取的 State，其中一个改设置，另一个随后更新 PID 或进度。
- 证据：窗口 A 保存新角色名后，窗口 B 保存 PID，磁盘上的角色名回退到旧值。
- 原因：每次写入整个内存字典；`RLock` 只保护本进程，`reload_pids()` 也只合并 PID，不能保护其他字段。
- 建议：短期引入按安装目录的跨进程锁、读改写事务和版本检查；长期考虑一个后台进程统一持有状态。仅给 `os.replace` 加重试不足以修复丢失更新。
- 验收：两个独立进程同时修改不同字段不互相覆盖，崩溃后状态可恢复。

### 6. P1：停止服务只认 PID，可能操作不属于本项目的进程

- 位置：`app/services.py:61`、`:76`、`:80`。
- 触发：上次服务结束后 Windows 复用 PID，而 `state.json` 仍保存旧 PID。
- 证据：在 `is_running()` 返回真时，代码直接发出 `taskkill /PID ... /T /F`，未核对可执行文件、创建时间或实例归属。复现中已拦截命令，没有杀真实进程。
- 建议：记录并核对进程身份，优先正常退出，超时后只终止本实例拥有的进程树。后续可评估 Windows Job Object，但需要保持“关闭界面后机器人继续运行”的产品行为。
- 验收：过期 PID 指向其他程序时必须拒绝终止；停止失败不能直接丢弃管理记录。

### 7. P1：构建解压没有限制输出路径

- 位置：`build/build.py:56`。
- 触发：构建读取包含 `..`、绝对路径等异常条目的 ZIP。
- 证据：测试包中的 `pkg/../escaped.txt` 被写到指定解压目录外。本次越界位置仍在专用测试临时目录内。
- 影响：受影响的是构建机器；是否可被外部攻击者利用取决于输入压缩包来源，没有验证真实供应链攻击。
- 建议：统一规范化条目，拒绝路径穿越、盘符、UNC 和异常链接；写入前确认目标仍在解压根目录下。为下载物建立固定版本和 SHA-256 清单。
- 验收：恶意条目被拒绝且无越界文件；正常单层目录包仍可正确解压。

### 8. P2：失败的“停止并退出”仍显示成功

- 位置：`app/web/app.js:546`、`:547`。启动、停止、切换、应用设置也存在忽略返回值的路径。
- 证据：模拟 `/api/quit` 返回 `{ok:false}`，界面仍展示“服务已停止”。
- 建议：所有有副作用操作检查结果；失败保留当前页面和重试入口；只有后端确认完成才显示成功。
- 验收：断连、权限失败、服务停止失败时不显示成功，不自动进入下一步。

### 9. P2：进度接口出错时前端继续读取不存在的 steps

- 位置：`app/web/app.js:156`、`:165`、`:353`、`:618`、`:640`。
- 证据：`S.progress={ok:false,message:'...'}` 时，`miniProgress()` 抛出读取 `length` 的异常。
- 建议：在统一 API 层判断 HTTP 状态和响应结构；将“断开、重试中、任务失败”与正常进度分开。轮询串行执行，离开页面后取消旧请求。
- 验收：服务重启或接口返回 500 时界面不崩溃，显示可恢复状态，连接恢复后继续刷新。

### 10. P2：旧校验结果覆盖新输入的状态

- 位置：`app/web/app.js:245`、`:257`、`:258`、`:265`。
- 证据：先请求 key-one，再请求 key-two；key-two 校验失败先返回，key-one 成功后返回，界面最终把当前 key-two 显示为“可以用”。
- 边界：后台保存仍会检查实际值，因此本轮没有发现凭此绕过后台密钥校验。
- 建议：输入时立即清除旧结果；请求带递增序号，结果仅作用于仍匹配的输入及页面；可取消的请求用 AbortController。
- 验收：人为调换响应顺序时，页面始终显示当前输入对应的状态。

## 其他值得安排的优化

- **备份与恢复**：提供角色、聊天、记忆的备份入口；恢复前显示版本与内容范围。凭据默认不导出，必要时采用单独加密导出。Windows DPAPI 数据不能假设能在另一台电脑直接解密。
- **明确的费用与能力开关**：当前语音和记忆均为必填；费用锁只是编辑确认。可将基础文字聊天作为最短流程，再按需启用语音和记忆。需同时改界面、后端校验、安装步骤和插件启用，不能只隐藏输入框。
- **可复现构建**：目前版本常量没有对应完整输入校验，`get-pip.py`、`7zr.exe` 等 URL 可变，依赖安装也未锁定全部版本。增加构建清单、校验和、依赖锁及可诊断的下载失败重试。
- **运行诊断**：分开显示 QQ 连接、聊天模型、语音、记忆的状态；“QQ 在线”不等于所有能力都正常。提供脱敏诊断包，避免用户手动发送完整配置。
- **隐私说明与凭据文件**：State 使用 DPAPI，但 AstrBot 运行配置中的 API Key 及“我的信息.txt”包含明文内容。界面的“密钥加密保存”应说明范围；限制文件访问权限，后台凭据导出应由用户主动操作。
- **本机接口加固**：静态首页公开嵌入 token 且没有 Host 白名单；建议增加 Host/Origin 检查。这里只确认缺少防护，没有完成 DNS rebinding 的浏览器攻击验证，不把它称为已证实的远程漏洞。
- **卸载路径约束**：`checks.check_install_path()` 实测接受含 `%REVIEW_PATH%` 的目录名，而卸载脚本把路径直接写入 CMD 命令。需防止环境变量展开改变路径，并校验安装目录标记、根目录和链接边界。本轮没有执行该特殊路径的卸载，不将其列入已复现的 10 项。
- **弹窗可访问性**：确认弹窗有 `role=dialog`，但没有完整焦点约束和关闭后的焦点恢复；普通确认默认聚焦确认键。可用原生 `dialog` 或补全键盘行为，危险操作默认聚焦取消。
- **自动化测试纳入项目**：原有 112 项测试未覆盖本次异常路径；前端检查脚本目前主要在忽略目录 `.tmp`。把关键场景转为正式回归测试，再配置 Windows 持续集成。无需为纯文案修改堆积测试。

## 需要一起讨论的较大改动

### A. 服务是否改为可选

建议方向：只填写聊天服务即可开始文字聊天；语音与长期记忆分别启用、分别测试、分别关闭。开启前解释数据发送和费用，不将任何云服务标成永久免费的承诺。

收益：第一次使用更容易，语音故障不会阻塞整个安装。代价：需要修改配置模型、安装任务依赖、插件开关和回归测试；已有配置需迁移。

### B. 是否统一一个后台管理进程

建议方向：所有窗口连接同一安装目录对应的后台，由后台统一管理配置、安装任务和子进程；关闭窗口与停止机器人保持两个明确动作。

收益：减少窗口间状态覆盖与重复启动，便于后续托盘、诊断、备份。代价：涉及启动方式、进程退出和恢复，属于中等规模重构。短期也可以先用跨进程锁和事务化状态更新控制风险。

### C. 升级及数据目录是否分离

建议方向：程序版本和用户数据分离，更新到新版本后切换入口；失败回退。备份不需要复制可重新下载的运行环境。

收益：升级更可靠、数据边界更清晰。代价：需兼容已有安装路径、快捷方式和状态格式。可以先做安全复制回退，再讨论目录迁移，不必一次完成。

## 建议执行顺序

1. 第一轮：修复账号数据清理、收费校验、安装恢复、更新回退、进程归属和解压边界；补上针对性的回归测试。
2. 同轮或紧接着：修复状态覆盖、接口错误显示、校验竞态；完成一次包含故障注入的六步浏览器验收。
3. 讨论并确定 A/B/C 中要做的产品和架构调整，再实施；保持现有海洋蓝视觉。
4. 最后安排真实 Windows 构建安装验证、受控额度下的真实接口验证、发布材料检查。只有收到明确上传指令才进行 Git 提交/推送相关工作。

当前建议先做第一轮可靠性修复，不建议现在投入整体框架迁移、多实例管理或复杂插件市场。
